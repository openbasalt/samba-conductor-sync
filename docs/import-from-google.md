# Import from Google Workspace

A company that already lives in Google Workspace and starts its Samba AD
from scratch has its people in Google, not in AD. The import creates them
in AD once, from the Google directory, so that the normal AD to Google sync
can then adopt each existing Google account by address (`policy.adopt =
"email"`, see [mapping.md](mapping.md#adopting-an-existing-google-workspace)).
After the import, AD is the source of truth as usual.

The import is a one-time bootstrap, not a second sync direction: nothing is
kept in step from Google to AD afterwards.

## Who does what

The work is split so that no single component gains rights it does not
already have:

| Component | Does | Never does |
|---|---|---|
| conductor-sync | reads the Google directory with the read-only Directory API scopes (`admin.directory.user.readonly`, `admin.directory.group.readonly`) and returns an import plan (management API operation `import.plan`, or `conductor-sync import-plan` on the command line); audits the read with the acting administrator | any write to Google (no request other than reads); any write to AD (its AD account stays read-only); recording a run or a plan |
| conductor | asks for the plan as the signed-in administrator, shows it, checks it against AD (conflicts, logon names), and creates the AD users and groups with the administrator's own credentials after a full preview, re-authentication (password and a fresh second factor) and with one audit entry per object | talking to Google; deleting or changing an existing AD object (an existing group only receives missing members) |

Passwords are never imported: the Directory API does not return them. No
password travels to Google either: conductor never talks to Google, and the
sync's later adoption of an account sends no password
([design.md](design.md#passwords)).

## What is read

For each Google account in the plan: the primary address, given and family
name, org unit path, suspended and administrator flags, aliases (for
information), and the fields the sync can map: title and department (the
primary organization), employee ID (the `organization` external ID), work
and mobile phones. For each group: address, name, description, aliases, and
its members that are in the same plan (accounts and nested groups);
other members (external addresses, accounts left out) are counted only.

## Filters

| Filter (`import.plan` / CLI) | Default | Effect |
|---|---|---|
| `org_units` / `--org-unit PATH` | all | only accounts in these org units (`/Sales`); with `sub_org_units` / `--sub-org-units`, also the org units below them |
| `member_of` / `--member-of ADDRESS` | none | only accounts that are members of at least one of these Google groups (nested membership counts) |
| `include_suspended` / `--include-suspended` | off | suspended accounts are left out unless set; included ones are created disabled in AD |
| `include_admins` / `--include-admins` | off | Google administrators (including the sync's admin subject) are left out unless set |
| `groups` / `--groups` | off | also return groups: all of them, or only `group_emails` / `--group ADDRESS` |
| `skip_empty_groups` / `--skip-empty-groups` | off (on in conductor's form) | leave out groups without any member in the plan, directly or through nested groups |
| `max_users`, `max_groups` | 500, 200 (at most 5,000 and 1,000) | the plan's size; objects beyond are counted as left out (`limit`) |

A group named in `member_of` or `group_emails` that does not exist in
Google stops the read with an error: a filter never silently selects nobody
or everybody. Accounts that already carry the sync's ownership marker are
always left out (`managed`): they come from AD already. Every plan lists
why objects were left out (`suspended`, `admin`, `managed`, `limit`,
`empty`, and `filtered` as a count), the org units with their number of
accounts and the groups (to choose filters), and warns about addresses
outside the sync's allowed domains (`domain-not-allowed`: the sync would
not adopt them).

## What conductor creates

Users, in the OU the administrator picks (one OU for all; it should be one
of the sync's `source.user_bases`):

| AD attribute | Value |
|---|---|
| `mail` | the Google primary address (this is what the sync adopts by) |
| `sAMAccountName` | see "Logon names" below |
| `userPrincipalName` | `<logon name>@<realm>` |
| `cn` | given and family name; when that name is taken in the OU, `Name (logon name)` |
| `givenName`, `sn`, `displayName` | from Google |
| `title`, `department`, `employeeID`, `telephoneNumber`, `mobile` | from Google, when set |
| password | 32 random characters generated by conductor, sent once in the create request, never shown, logged or stored |
| `pwdLastSet` | 0 (must change at next logon) |
| enabled | yes by default (see below); always disabled for a suspended Google account |

Groups, in the OU picked for groups (one of the sync's `source.group_bases`,
for example an OU named Google Groups): global security groups with `mail` =
the Google group address, `cn` = the Google name, `description`, and as
members the imported users (and users already in AD with the same address)
and, in a last step, the imported groups (nesting is kept).

## Logon names

The logon name is the part of the address before `@`, in lower case, when
it is a valid `sAMAccountName` as it is (at most 20 characters, none of
`" / \ [ ] : ; | = , + * ? < > @`, no spaces, not ending with a dot) and is
not used by any AD object. Otherwise a fallback template is rendered, by
default `{given}.{family}`; placeholders are `{given}`, `{family}` (its last
word), `{g}` and `{f}` (first letters) and `{local}`; accents are folded to
ASCII and other characters dropped, and the result is cut to 20
characters. When neither is free, the user is not created and the preview
says so: conductor never invents numbered names. Groups use the address's
local part, then the group name, up to 64 characters.

## Conflicts and skips

Conflicts never stop the job; each one is a row of the preview without
changes and with its reason:

| Case | Result |
|---|---|
| an AD user already has the address (`mail`, `userPrincipalName` or an SMTP `proxyAddresses` entry) | left as it is; it is still used as a member of imported groups |
| several AD objects have the address | left out |
| no free logon name, or the name and its `(logon name)` variant are both taken in the OU | left out |
| an AD group already has the address | not created; only the plan's members it lacks are added |
| that group is privileged (an administrators' group or another protected group) | never changed |
| beyond the run's limit | left out; the next run creates it |

An OU that does not exist stops the job before anything is written.

## Enabled or disabled

New accounts are enabled by default, with a password nobody knows and a
forced change at next logon. While nobody knows the password an enabled
account is as unusable as a disabled one, and enabled is what the sync
expects: an enabled AD user in scope adopts its Google account on the next
run, while a disabled AD user never adopts one (`disabled-not-adopted`). The
administrator then onboards each person in conductor (Users > the account >
Reset password, with "must change at next sign-in").

The alternative, chosen in the form, creates every account disabled.
Nothing is adopted until an administrator enables the account; enabling it
later is a separate audited action. Prefer it when the AD scope of the sync
should grow person by person through enabling, rather than through an
include group.

A Google account that is suspended is always created disabled: the sync
then leaves the suspended Google account alone.

## Running it again

The import is idempotent: everything is decided against what AD holds at
that moment, and what exists by address is never created twice. A per-run
limit (conductor's form, 50 objects by default) bounds each job; the rows
beyond it say so, and running the import again creates the rest. A failed
row can also be retried from the job page (it is validated again first).
Nothing is ever deleted.

## After the import

1. In the sync settings: `policy.adopt = "email"`, the first
   `mapping.primary_email` template `{mail|lower}` (and the first
   `group_email` template `{mail|lower}`), the import OUs below
   `source.user_bases` and `source.group_bases`. conductor's import page
   warns when one of these does not hold, and when `source.include_groups`
   is set (imported users are synced only once they are members).
2. Keep `mode = "dry-run"` and generate a plan. It should show only
   `user.adopt` and `group.adopt`, with no field change for the imported
   accounts (AD holds the Google values), and no `user.create`.
3. Apply it by hand. Adoptions count toward `max_updates` and
   `max_touched_percent`; the first batch usually needs the override (see
   the rollout in [mapping.md](mapping.md#adopting-an-existing-google-workspace)).

## Command line

```
conductor-sync import-plan [--org-unit PATH]... [--sub-org-units] [--member-of ADDRESS]...
                           [--include-suspended] [--include-admins] [--groups] [--group ADDRESS]...
                           [--skip-empty-groups] [--max-users N] [--max-groups N] [--json]
```

It prints the same plan as conductor's page and writes nothing but an
audit entry (`import.plan`). It is the safe first step against a real
tenant: run it, read the plan, then use conductor to create the objects.

## Checking a run against a real tenant

1. Run `conductor-sync import-plan --groups --json` with
   `CONDUCTOR_SYNC_REQUEST_LOG=<file>`; every line of the request log must be
   a `GET`.
2. Compare the plan with the Admin console: counts per org unit, suspended
   and administrator accounts left out, group members.
3. Import a small org unit with conductor into a test OU, check the AD
   objects (`mail`, names, disabled or enabled, `pwdLastSet` 0), and generate
   a sync plan: only adoptions, without field changes.

## Management API

`import.plan` takes the filters above (`syncapi.ImportPlanParams`) and
returns `syncapi.ImportPlan`. It is not a mutation (no state changes) but
is audited (`api.import.plan`, the filters and the counts, no personal
data). An answer that would exceed the message limit (4 MiB) is refused
with a request to narrow the filters. Adding the operation did not change
the protocol version: a conductor that does not know it never sends it, and
an older conductor-sync answers that the operation is not allowlisted.
